# Launch plan — 2026-08-10

Three enterprise teams start **Monday 2026-08-10**, and public self-serve opens at the same time.
Everything has to be on `main` and deployed by **end of Sunday 2026-08-09**.

Two Claude Code sessions are working this in parallel, in separate worktrees. This file is the
contract between them: what launch means, who owns which files, and what is deliberately not being

## What "launched" means

A person who has never seen Mneia can, unaided:

1. Sign up at `app.mneia.dev`, or accept an invitation from a colleague
2. Land in the **same workspace** as their colleague — not an island
3. Install the CLI and the MCP server from npm
4. `mneia login`, checkpoint from one session, rehydrate in the next
5. Not be able to read another workspace's rows, and not be able to run up an unbounded inference bill

Anything that does not serve one of those five is not launch work this weekend.

### The gap that decides the weekend

`bootstrapSoloAccount` (`apps/web/src/server/account.ts:14`) hands **every** signed-in user their own
workspace, team, actor and membership. `AccountStore` (`apps/web/src/server/store/account-store.ts:33`)
exposes exactly that one method. There is no invite, no join, no second way into a workspace.

So two colleagues at the same enterprise sign up and land in two isolated tenants. RLS then does
exactly its job and makes sure they can never see each other's work. The product is single-player
today, and §8.1 rule 3 is explicit that the moat clock only starts when a second actor writes to a
shared project. **This is the launch blocker.** It is MNE-126, pulled out of M4 into M1 on 2026-08-07.

## B1 · MNE-126 — Workspaces, invites, and membership

**Branch:** `feat/mne-126-workspace-invites` · **Ticket:** https://linear.app/mneia/issue/MNE-126

The whole point of the product, and it does not exist. Read the ticket — it carries the full shape.
Summary of what has to be true:

**Schema (migration `0015`).** An invitation table: `workspace_id` on every row, single-use token
hash (never the token itself), inviter actor, invited email, role, expiry, accepted-at. `ENABLE` and
`FORCE ROW LEVEL SECURITY` with the workspace-isolation policy keyed on the `mneia.workspace_id`
GUC — copy the pattern from `0002-core-entities.ts`, do not invent a new one. Run `pnpm db:snapshot`
and commit `db/structure.sql` **in the same commit**; CI fails the PR otherwise.

**Store.** Add invite / list pending / revoke / redeem beside `bootstrapSoloAccount`. Redeeming
creates the `actor` and `team_member` rows inside the **inviting** workspace. The invariant that
matters: redeem must match on the Clerk-**verified** email address, never on an email supplied in the
request body. An unverified email in the payload is an invitation to walk into someone else's tenant.

**Resolver.** `resolveCurrentAccount` currently bootstraps solo unconditionally. It has to check for a
pending invitation matching the verified email first, and only bootstrap solo when there is none.

**Web.** A page to invite and see pending invitations, and an accept route. Match the existing
`/welcome` server-action style — the codebase does not use client-side fetch for this.

**Events.** Every new write path emits its §17 event. Standing rule 5, and MNE-51's coverage test
enforces it — a write with no event fails the suite, it is not a review nit.

**Done when:** a user invites a teammate by email, that teammate accepts and lands in the *same*
workspace, both write to the same project, and an integration test proves a third party in another
workspace sees none of it.

### Traps, all of them real in this repo

- **RLS bites during redeem.** The invited person has no actor in the target workspace yet, so a
  `withScope` transaction scoped to *their* workspace cannot see the invitation row. Resolve the
  invitation in a scope set to the **inviting** workspace. Do not reach for `MNEIA_ALLOW_RLS_BYPASS` —
  it exists for migrations and for nothing else, and using it here is how one tenant reads another.
- **Never take `assertedBy` or `humanConfirmed` from a caller.** MNE-216 just removed exactly that.
  Actor kind is read from the `actor` row, never from a payload.
- Enterprise sign-ups will arrive on **corporate SSO via Clerk**. Do not assume a password identity.
- Seat billing is **not** in scope — MNE-141/142 are M2 and Stripe is not wired. Invitations are
  unmetered this weekend; note it in the PR so it is a known decision rather than an oversight.

## B2 · MNE-105 — npm publish and install documentation

**Branch:** `feat/mne-105-npm-publish` · **Ticket:** https://linear.app/mneia/issue/MNE-105

Public self-serve is meaningless if there is nothing to install. Right now nothing is publishable:
all three packages sit at `version: 0.0.0` with no `publishConfig`, and scoped packages default to
**restricted** on npm — publishing without `access: public` either fails or silently ships something
nobody outside the org can install.

- `@mneia/core`, `@mneia/cli`, `@mneia/mcp-server` → a real version (`0.1.0`), and
  `publishConfig: { access: "public" }` on each.
- Confirm the `@mneia` scope actually exists on npm and that the token in CI can publish to it.
  If the scope is taken, **stop and say so** — that is a naming decision, not yours to make.
- `files: ["dist"]` is already right. Verify with `npm pack --dry-run` that the tarball contains built
  JS and type declarations and no source, no `.env`, no tests.
- `@mneia/cli` and `@mneia/mcp-server` depend on `@mneia/core` by package name. Whatever the workspace
  protocol resolves to must become a real semver range in the published manifest, or install breaks
  for everyone outside this repo. Verify by installing the packed tarball into a scratch directory
  outside the monorepo — a workspace-linked install will pass and prove nothing.
- READMEs must match reality. **Do not restate self-hostability, offline operation, or "content never
  leaves your machine"** — those claims were revoked on 2026-07-28 (§11.1, §15) and a registry listing
  is exactly the public surface that rule names.

**Done when:** `npx @mneia/cli init` works on a clean machine against `app.mneia.dev`, and the
published README matches what the binary actually does.

## Rules that will fail your build if you skip them

- **Branch → commit → PR.** Code lane. The `git-lane-guard` hook rejects a commit with no `MNE-nnn`
  in the subject. Branch `feat/mne-126-<slug>`, subject `MNE-126: <imperative>`, PR body `Closes MNE-126`.
- **No `Co-Authored-By`, no "Generated with Claude Code"** trailers.
- **No code comments** unless the ticket asked. Rationale goes in the commit message.
- **Run `pnpm test` before opening the PR** — it needs `DATABASE_URL`; without one the integration
  suites skip themselves and prove nothing. `pnpm -r build`, not bare `pnpm build`, or app type errors
  slip through.
- **Migration + `db:snapshot` in one commit.** A migration PR also gets a Neon branch and a posted
  schema diff — read it before merging.
- **Do not deploy to production.** `CLAUDE.md` requires asking the founder first, every time. Merging
  to `main` triggers `deploy-web.yml` on paths touching `apps/web`, `packages/core`, `deploy/`, or the
  Dockerfile — so a merge *is* a production deploy. Get the founder's review before merging B1.
